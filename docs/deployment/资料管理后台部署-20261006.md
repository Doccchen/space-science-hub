## 1. 发布前准备

- 保留当前代码、Compose、环境文件、app/admin 镜像 ID；环境文件和运行数据留在服务器，不进入发布包或聊天输出。
- 通过现有 `tools/backup_review.py` 一致性备份新闻库和关联图片；AI 会话库使用 SQLite backup API。已经存在管理库时，再使用下方管理库备份命令。跨库/代码的联合回退点需暂停后台修改及其他写入者后取得。
- 核对现有 Compose 项目名、实际数据卷和端口，不另建空数据卷。默认后台仅监听服务器 `127.0.0.1:8090`；SSH 转发到本地 `18080`，`ADMIN_ORIGIN=http://127.0.0.1:18080`。
- 已有管理员账号继续使用。尚未初始化时按照现有人工审核部署说明执行 `tools/admin_user.py`，不设默认密码。

本阶段涉及 `backend/management_store.py`、`backend/resource_admin.py`、`backend/resources.py`、`backend/admin_app.py`、`admin_web/index.html`、`admin_web/admin.js`、`admin_web/admin.css`、`admin_web/resources.js`、`tools/resources_manage.py` 与 `compose.yaml`。请审阅这些文件的差异；不要直接覆盖服务器已有环境设置。

## 2. Compose 与上线

本地 Compose 已让 app/admin 都使用 `space-news-app` 镜像，两个服务的 `MANAGEMENT_DB_PATH` 均为 `/data/site-management.sqlite3`，沿用同一个 `news-data:/data` 卷。将这些变化合并到服务器 Compose，同时保留现有端口、环境变量、采集开关及 AI 设置。`RESOURCES_PATH` 若有自定义，迁移时使用对应的真实目录路径。

另一种取得上线前完整数据快照的方式：先构建候选镜像，然后停掉 app/admin，将停止的旧 app 容器 `/data/.` 复制到服务器私有备份目录。这样新闻库、AI 库、管理库及图片都没有活动写入者；SQLite WAL/SHM 也必须一并保留，不能只拷主库。确认备份成功后再重新创建服务。停止服务到新服务启动之间会有短暂不可用。全数据备份及代码备份应保存在数据卷之外，勿使用 `down -v` 或移除旧数据卷。

在原部署目录、原 Compose 项目中执行；示例默认路径为 `/opt/space-news`：

```bash
cd /opt/space-news
docker compose config --quiet
docker compose build app
docker compose --profile review up -d --no-build --force-recreate app admin
docker compose --profile review ps
```

重建后确认两容器镜像 ID 一致、原共享数据卷未变，新闻、AI 和资料原功能正常。首次迁移前公开资料仍使用原 JSON；私有资料页提示需先迁移。以上健康检查不会调用百炼。

显式迁移。工具不会在每次启动时导入，也不会覆盖数据库中的后续修改：

```bash
docker compose exec app python tools/resources_manage.py migrate --source /app/content/resources.json
docker compose exec app python tools/resources_manage.py inspect
```

首次期望输出 `imported=true`、`source_count=28`、`current_count=28`、路径/ID 对比一致。源目录全部验证后才事务导入，原 ID、路径、元信息和排序保留。重复运行输出 `imported=false`；若资料已修改，路径/ID 对比不一致可正常发生，工具只报告、不覆盖。

启用后 `/data/site-management.sqlite3` 是权威目录，并保留 `/data/site-management.resources-enabled` 标记。库丢失/损坏时前台资料 API 返回 503，不回退旧 JSON；新闻健康检查独立。

## 3. 管理与人工验收

用原 SSH 转发方式打开后台，登录后选择“资料管理”。

1. 检查原 28 份资料及其排序、封面、上架状态；前台分类、搜索和分页保持原行为。
2. 编辑测试资料，查看变更后确认保存；刷新前台，原下载入口应 302 到新地址。
3. 下架后，前台不显示该资料，直接访问下载入口应为 404。下架仅关闭本站入口，不能撤销已公开的 OSS 文件或此前下载的副本。
4. 在两个窗口编辑同一资料；后保存者应收到冲突提示，并保留其输入供重新核对。
5. 从历史恢复，确认产生新修订，且全部字段和上下架状态恢复。
6. 新增默认下架；封面可为空，或选择现有本地封面。核对后单独上架。
7. “检查文件”仅对已保存的固定 OSS 地址发 HEAD，不跟随跳转，每份资料至少间隔 10 秒、全站每分钟最多 10 次。200 表示元信息可取得，404 表示服务报告未找到，403/405/重定向/超时为无法自动确认。返回大小须点击填入，再确认保存。地址校验及 HEAD 都不能证明 PDF 内容有效；以浏览器下载核对为准。
8. 重启 app/admin 后再核对保存记录。后台读写接口需登录，写操作还需 Origin 和 CSRF。

元信息（作者、标签等）仅在后台内存表单中编辑，页面刷新/离开会提示未保存修改；列表封面由私有鉴权路由提供，不需要放开后台 CSP 外部图片来源。

## 4. 备份与故障恢复

使用新的、尚不存在的输出路径。示例日期后缀应按实际操作时间设置：

```bash
docker compose exec app python tools/resources_manage.py backup --output /data/backups/site-management-20261006.sqlite3
```

该命令通过 SQLite backup API 得到一致性快照并执行完整性检查，不直接复制正在写入的主库。将该快照和 `.resources-enabled` 标记安全保存到数据卷以外的备份位置，并记录对应代码版本。工具不会覆盖已有备份路径。

恢复时先停止 app/admin，核对备份完整性和目标原数据卷；保留故障库及其 WAL/SHM 作为证据，确保不存在运行中的连接，再替换管理库及启用标记。不要把故障库的 WAL/SHM 与恢复后的快照混用。文件所有者应允许容器 UID/GID `10001:10001` 读写。恢复后启动两个容器，使用 inspect 与浏览器核对。不得通过删除启用标记来伪装已恢复。

## 5. 代码回退

资料历史恢复优先用于日常误修改。退回不认识管理库的旧代码时，先停止后台写入并导出当前目录：

```bash
docker compose exec app python tools/resources_manage.py export --output /data/backups/resources-current-20261006.json
```

将导出目录复制到服务器代码目录，校验后在旧 Compose 的 app 环境中设置 `RESOURCES_PATH=/data/backups/resources-current-20261006.json`，确保旧容器仍使用同一数据卷。这样旧版即便把原 JSON 打包在镜像里，也会读取此次导出记录。重新创建旧 app 和对应旧 admin；不要让新后台继续修改旧版正在使用的静态导出目录。

保留当前管理库、标记和备份供恢复新版本使用。该回退不会改动百炼环境配置或重置 AI 额度。未完成目录导出及实际读取核对时，不得声称仅回退镜像即可保留后台资料修改。
