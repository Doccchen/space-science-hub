# 研究生科研文献助手：省赛开放主题作品实施方案

版本：2026-10-04。范围：网站与可运行作品；不包含 PPT、视频制作。

## 1. 目标与前提

在 10 月 11 日前上线可以真实查询的第一版，10 月 18 日前完成核心功能，10 月 25 日前形成稳定版本。11 月 2 日是用户给定的准备截止时间，不把网站开发拖到最后一天。

目前已知：用户有简单网站搭建经验，作品暂定科研文献查询，帮助研究生的科研工作。具体学科、数据源、模型 API、已有服务器、预算、每日投入时间尚未确定。本方案按一名主要开发者、可持续投入、使用已有模型 API、优先复用熟悉部署方式制定；日期是目标，需要根据上述条件调整。

关于赛事：湖南师范大学教务处发布的通知列出省赛开放主题作品和成果展示视频、匿名评审，以及 11 月 2 日 22:00 前提交。用户所属赛区和最新作品细则仍未确定，不能把该通知直接当成用户赛区的完整规则。第一天核对作品格式、匿名要求、AI 使用说明、是否接受网站链接及是否需附源文件，避免仅有网址却不满足提交形式。

来源：[湖南师范大学教务处通知](https://jwc.hunnu.edu.cn/info/1093/10943.htm)。实际执行以用户赛区最新要求为准。

## 2. 作品定位

建议定位为：面向研究生选题和文献初筛的“可追溯 AI 科研文献助手”。用户用自然语言描述研究方向，系统构建检索条件、查询真实文献、筛选与对比，并给出 DOI、来源和判断依据。

作品的一句话介绍：帮助研究生把研究问题转化为可复现的检索条件，找到并对比相关文献，减少检索与初筛时间，让每条文献和分析结论都有可核对的依据。

主题已暂定为科研文献查询。第一版检索可以面向多个学科，但验证和展示聚焦用户熟悉的一个学科，准备三个真实研究问题。文献搜索结果不能证明“已完整覆盖全部相关研究”，样本年份统计也不能直接当成整个领域的发展趋势。

数据源建议：OpenAlex 作为主检索候选，Crossref 用于 DOI 元数据核验。二者均先在目标部署环境实测；OpenAlex 当前访问要求、额度与费用在开工时核对，不能假定无限免费。Crossref 官方提供文献元数据的搜索、筛选与 DOI 查询接口；摘要可能缺失且部分摘要有版权限制。

来源：[OpenAlex 官方文档](https://help.openalex.org/)、[Crossref REST API](https://www.crossref.org/documentation/retrieve-metadata/rest-api/)。CNKI、LeapSpace 的个人竞赛访问权限不能直接推定为网站可调用或可再分发的 API 权限，第一版不依赖其登录抓取。

首版示例任务：用中文描述研究方向 → 展示可编辑英文关键词与同义词 → 限定 2022—2026 年、文献类型和开放获取条件 → 返回候选文献 → 选取 3—5 篇比较 → 导出候选清单与检索记录。年份只是示例，可由用户调整。

对比字段以标题、作者、年份、期刊、DOI、可获取摘要和开放获取入口为主。研究方法、创新点与局限只有摘要中明确支持时才整理，并标注“基于摘要”；无摘要时明确缺失。全文问答、自动综述和所谓研究空白发现放到后续版本。

## 3. 第一版功能边界

必须完成的闭环：提出问题 → 确认条件 → 查询真实数据 → 展示结果 → 查看来源 → 导出结果。

| 功能 | 第一版内容 | 完成判据 |
|---|---|---|
| 查询入口 | 自然语言输入、3—5 个示例问题 | 用户能明确知道网站能查什么 |
| 条件理解 | 提取主题、地区、时间、指标；必要时追问 | 模糊条件不被悄悄替换成任意值 |
| 数据查询 | 1 个主要数据源，最多再接 1 个补充源 | 页面结果来自真实工具返回 |
| 结果展示 | 摘要、表格；适合比较的数据再绘图 | 数值、单位、年份和表格保持一致 |
| 证据展示 | 来源名称、URL、获取时间、口径或原文位置 | 用户能核对每个关键结论 |
| 连续追问 | 在当前结果上改时间、地区或筛选条件 | 不丢失关键条件，能重查数据 |
| 导出 | 文献清单 CSV、带来源的 Markdown 摘要；第二阶段补 BibTeX | 导出内容与页面一致，引用字段经过核验 |
| 异常处理 | 无结果、条件不明确、API 超时、超出范围 | 明确说明情况，不编造答案 |

第一版不安排账号体系、支付、多智能体协作、通用网页抓取、大型管理后台和复杂推荐功能。CSV/表格类数据先用结构化查询；文档类主题再补文档检索，不预先引入向量数据库。

## 4. AI 智能体的实现

流程：用户输入 → 模型提取查询条件 → 服务端校验 → 调用受控查询工具 → 计算与整理结果 → 模型根据结果解释 → 页面呈现来源。

模型负责理解语言和解释结果。过滤、统计、排序、单位转换由确定性程序完成。第一版采用一个智能体加少量工具，不依赖多个智能体互相讨论。

建议工具接口：search_papers、get_paper_detail、verify_doi、compare_papers。DOI 规范化后去重，无 DOI 文献用来源 ID 并辅以标题与年份判断，避免误合并。跨源字段冲突保留出处并提示差异。数据查询工具限定已接入的数据源、允许字段和结果数量；若使用数据库，只提供受控只读查询。模型不得直接执行任意代码或任意数据库语句。

关键约束：

- 数字必须对应工具结果，来源链接由服务端提供，禁止模型自行生成引用。
- 文档中的命令、提示词和网页文字属于资料内容，不能改变智能体工具权限。
- 无足够证据时返回“未找到”或“需要补充条件”，并说明已查询的范围。
- 每次请求设置工具调用次数上限、超时与结果长度限制；失败时保留已找到的有效证据。
- 界面展示真实阶段，如“解析条件”“查询数据”“整理结果”；不展示虚构执行过程或模型内部思考。

数据结构至少保留：记录 ID、来源、来源 URL、获取时间、数据所属时间、指标或标题、值、单位、口径、许可或使用限制。获取时间和数据年份不能混为一谈。

## 5. 技术与部署建议

默认组合：React + TypeScript + Vite 前端，FastAPI 服务端，SQLite 保存结构化数据与缓存，模型通过服务端调用。选择理由：前端方便实现查询界面和图表，Python 方便数据整理与查询，单实例 SQLite 能减少初期运维工作。

若用户已有熟悉且可用的全栈 JavaScript 项目或智能体平台，优先沿用；在第一天完成一次网页到后端、后端到模型和数据源的真实调用后锁定方案。不要同时维护两套后端。

已确定硬件：用户有阿里云 2 核 2G 服务器，计划通过 Docker 部署。保留 React + TypeScript + Vite、FastAPI、SQLite，采用 Docker Compose 管理两个容器：Nginx 提供已构建的前端静态文件并反向代理 /api，FastAPI 负责智能体、文献 API 和数据缓存。SQLite 文件挂载到后端持久卷；无需单独数据库容器。网站同域访问。

部署结构：浏览器 → Nginx（HTTPS、静态前端、/api 代理）→ FastAPI（单个 Uvicorn worker）→ 外部模型 API / OpenAlex / Crossref。SQLite 用于结果缓存、文献记录和少量会话数据；查询流程采用异步 HTTP，避免等待外部接口时阻塞服务。

2G 内存下的初始部署配置建议：Nginx 内存上限 128MiB，后端上限 768MiB；这是限制与预算建议，不是已测量的实际占用。至少给系统、Docker 和突发开销预留其余内存；若服务器已有其他服务，先核对可用资源。后端先用单 worker，限制同时进行的 AI 任务为 2—3 个，满额时明确提示稍后重试，完成测试后再调整。Docker 容器默认没有资源限制，应在 Compose 中明确配置并确认生效。

服务器只运行构建后的应用，不常驻 Vite 开发服务或前端构建环境。优先在本机或 CI 构建前端与镜像，推送后由服务器拉取；镜像架构必须匹配服务器。模型与 embedding 如有需要均走外部 API，不在此服务器部署本地大模型。首版不额外自托管 Dify、向量数据库、Elasticsearch 或独立任务队列。

SQLite 必须持久化并定期执行一致性备份，不能只把运行中的数据库主文件当作完整备份；如开启 WAL，也需要正确处理备份。重建容器后验证数据仍在。配置自动重启、健康检查、日志轮转，避免日志与旧镜像占满磁盘。

服务器地域、操作系统、磁盘、带宽、已有服务和域名情况待核对。第一天从服务器实测模型 API、OpenAlex、Crossref 的 DNS、HTTPS 与响应时延，并从用户网络实测网站。若涉及中国内地服务器的域名公开访问，核实阿里云当前备案要求与现有备案状态，纳入上线排期；使用 IP 不应当作规避备案的部署方案。以上条件未核实前，不保证现有配置的并发容量或公开访问日期。

上线必须配置 HTTPS、服务端环境变量、请求限流、单次结果上限、模型用量上限和错误日志。密钥不出现在浏览器代码或公开仓库。匿名试用优先；查询日志只保留排障必要信息。

如数据 API 暂时不可用，可提供明确标注来源和采集日期的历史数据快照查询，或已保存结果。不得将缓存或预录结果标成实时查询。

技术依据：[Vite 静态部署说明](https://vite.dev/guide/static-deploy.html)、[FastAPI 容器部署说明](https://fastapi.tiangolo.com/deployment/docker/)、[Docker 资源限制说明](https://docs.docker.com/engine/containers/resource_constraints/)。具体版本在开始开发时锁定。

## 6. 网站页面与技能分工

采用一个主查询工作台，加一个数据来源与方法说明页。主页面包含简短作品介绍、示例问题、查询输入、条件确认、真实查询进度、结果表格/图表、来源和导出入口。桌面端优先，手机端保证查询、结果和来源可用。

视觉重点是查询体验和信息可信度。图表由真实结果生成，注明时间和单位；装饰素材不得承担证据功能。

| 已安装技能 | 用途 | 使用阶段 |
|---|---|---|
| kb-retriever | 阅读本地资料、梳理来源和可用字段 | 主题与数据准备 |
| web-design-engineer | 工作台、结果展示、视觉系统和界面实现 | 原型与前端开发，主要使用 |
| gpt-image-2 | 必要时制作封面或主题插图 | 核心功能可运行后，按需使用 |
| beautiful-article | 如有需要，将作品方法整理成独立说明文章 | 核心功能完成后，可选 |
| web-video-presentation | 当前阶段不安排 | 后续另行考虑 |

上述技能是开发时的辅助能力。安装技能不会自动赋予网站用户模型能力、数据权限或后台服务；运行时智能体需单独实现。

## 7. 实施日程与退出条件

| 时间 | 工作 | 当阶段必须交付 |
|---|---|---|
| 10/4—10/5 | 定主题、核规则、验证数据与 API、选部署方式 | 一页需求说明、真实数据样本、10 个典型问题、可访问测试地址 |
| 10/6—10/8 | 打通首个查询链路，再完成界面原型 | 在线页面能回答一个真实问题并显示来源；主要页面方向确定 |
| 10/9—10/11 | 接入主数据源，补结果展示和错误状态 | 首版上线；3 个代表性案例可从头操作成功 |
| 10/12—10/15 | 补追问、比较、图表、导出、来源详情 | 核心功能完整，开始记录验证结果 |
| 10/16—10/18 | 完成关键测试，修复错误，冻结功能范围 | 可以交给他人独立试用的版本 |
| 10/19—10/25 | 小范围试用、改进易用性、修复稳定性问题 | 稳定线上版本、备份、部署说明、效果验证记录 |
| 10/26—11/2 | 保留网站维护与突发问题处理时间 | 只修影响使用的问题，避免大改 |

第一天若拿不到数据权限或无法连通，先换同主题的可用数据源，仍不可行再调整主题。10 月 8 日若真实查询链路未打通，停做视觉装饰并缩减范围。10 月 11 日若进度滞后，先削减第二数据源、复杂图表、长对话；保住真实查询与来源核验。

任务顺序：数据可用性 → 最短真实查询 → 提前部署 → 界面完善 → 扩展功能 → 验证与稳定化。上线不是最后一步。

## 8. 验证与作品完成标准

建立 30 个固定案例：10 个文献检索、5 个年份/类型筛选、5 个文献比较/DOI 核验、5 个连续追问、5 个无结果/缺摘要/模糊/异常问题。每个案例记录预期字段、来源和实际结果。检索任务没有唯一正确文献清单，需要由熟悉该方向的研究生建立相关性标注；对检索相关性、字段正确性和工具完成率分别评分，不混为一个指标。

目标：有效查询案例正确完成率至少 90%；所有已返回的关键数值与引用均能核对，不能容忍用编造结果凑通过率。测试至少覆盖一次模型超时、一次数据源失败、一次错误引用和一次服务重启后的数据恢复。

记录端到端时延中位数和较慢请求的时延，初期目标为多数典型查询 20 秒内完成，30 秒内没有结果就提示等待或失败。实际指标按模型、数据源和部署环境测量后调整，不承诺未经实测的性能。

邀请 3—5 名目标用户完成相同查询任务，记录完成率、耗时与反馈；与人工检索对比时保持任务和数据范围一致，并如实报告样本量。创新点可放在来源追溯、条件澄清、统计口径检查和可复现查询上，避免仅以“接入 AI”概括贡献。

作品完成交付：可访问的网址、网站源代码、数据来源与字段说明、部署/备份说明、固定案例与验证记录、3 个完整使用案例。按赛事最新要求补相应作品说明或源文件包装；此处不制作 PPT 或视频。

## 9. 开工前最少需要明确的信息

主题与目标人群已初步确定。下一步明确重点学科、首个数据源、现成模型/API、熟悉的开发/部署方式、可投入时间和预算。最关键的是数据可用性；其他事项可在第一日验证后确定。不得把当前校赛资料默认当成省赛作品内容。
