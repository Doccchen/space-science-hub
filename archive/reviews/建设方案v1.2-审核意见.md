# 《航天新闻网站——建设方案 v1.2》审核意见

审核日期：2026-10-05。
审核对象：E:/AI-GPT/.zcode/workspace/default/航天新闻网站-建设方案.md。
原方案未修改。本文结合本聊天既定需求、方案内部一致性及可获取的官方技术资料审核；没有在用户服务器运行采集器或调用付费模型。

## 总体判断

可作为新闻采集与展示的初步技术方案，不宜按当前版本直接进入全部开发。FastAPI、SQLite、Docker 和受控来源总体合适，来源性质标注及单源故障隔离值得保留。需要先确定范围、补齐证据链、修正去重与成本，并把部署及核心 Agent 前移。

## 开工前必须明确的事项

### 1. 产品范围发生变更，三模块与双版本输出缺失

位置：第4、138—146、204—212行。

本聊天最新定位是“航天新闻、科普 Agent、资料下载”三部分，Agent 基本功能为专业摘要与科普版本。新方案只有新闻聚合与新闻问答，缺少资料下载、文件上传管理，也未定义双版本科普输出。新闻问答可作为追加能力，但不等价于已讨论的科普适配。

建议先在需求章节明确：是否有意改变范围。若仍沿用现有方向，保留三个独立栏目；新闻详情提供“用 Agent 解读”；Agent 输出双版本，后续再补针对当前材料的问答。资料库首版仅管理员上传、资料元数据、访客下载，按文件条件选做 PDF 预览。不先开发复杂公开上传或长文档问答。

### 2. 原文依据没有数据来源与持久化路径

位置：第103—109、152—160、167—173、199行。

articles 仅有标题和摘要，却要求引用“原文第X段”、组装“原文要点”。没有说明段落如何获取、保存、定位及版本化。新闻摘要往往不包含足够参数与限定条件，不能支持文章范围内的任意问答。

建议区分：对外页面展示的摘要，与在允许条件下供内部核对的证据材料。引入 documents、evidence_chunks 或等价结构，至少保存文档ID、URL、章节/段落位置、证据片段、获取时间、内容版本或哈希。来源不能提供可用正文时，明确降级为“仅根据当前摘要”，相应缩减可回答范围。上传文件使用页码/段落定位。模型只能返回已有证据ID，引用文本与链接由服务端解析提供。

### 3. 提示词约束被写成事实保证，流式输出缺少核验顺序

位置：第146、166—173、221—223行。

低温度、资料包裹和拒答提示是辅助措施，不保证无幻觉。若直接流式显示未验证文本，错误数字可能先呈现给用户，之后才被发现。

首版建议：提取结构化事实 → 生成两版内容/回答与证据ID → 校验引用存在性、数字/单位、对象和限定条件 → 展示结果。先发送真实处理状态，输出正文在检查后发布；如一定要逐段流式，定义每段验证与失败处理。数值检查不能只用字符串是否出现，还要检查数值对应哪个对象、单位和时间。对未支持内容删除、拒答或标为待确认。另一模型复核仍不能替代人工抽检。

建立固定评测集，覆盖事实提取、术语解释、缺少参数、单位变化、预计与已完成、资料冲突、恶意指令、翻译限定词。评估事实一致性、引用有效性与可读性，不只评估回答是否流畅。

### 4. 去重规范会误合并文章与丢失独立来源

位置：第104、116、129行。

“去参数、统一https/小写”不可作为通用URL规范化规则。id、article等参数可能决定文章身份；路径区分大小写；http与https不能不验证就视作同一资源。同一事件的不同报道应分组而不是去掉。

建议：scheme和host规范化大小写，保留path与业务query；只去除明确已验证的跟踪参数；保留original_url与canonical_url；按来源+来源条目ID、规范化URL建立幂等键。不同报道保留独立记录，用event_id关联。“多家报道”不自动等于独立交叉验证，多站转载同一通稿仍是一条信息链。

依据：[RFC3986 §6.2.2.1](https://www.rfc-editor.org/rfc/rfc3986.html#section-6.2.2.1)。

### 5. 白名单约束需要覆盖实际请求与最终链接

位置：第12、50—52、118、127、133行。

只筛选SNAPI的news_site字符串，不能证明最终链接一定属于批准的域名；RSSHub入口合规也不能保证所有下游请求自动满足白名单。图片代理可能访问不同域名，用户提供URL或后续重定向也可能超出范围。

建议按source_id绑定经过审核的publisher域名、采集地址与内容规则；校验实际原文URL和重定向后的目标。图片使用单独的允许域名列表，限制HTTP/HTTPS、重定向、响应大小、类型、超时与并发，拒绝私网和本机地址。不把代理设计成任意URL转发服务。没有可用图片时使用无图版式，无需强行代理。

“只存摘要”“标注来源”不应写成自动规避使用权限问题。每个来源记录内容/图片/下载资料的允许使用方式；不确定时仅展示必要的标题与原文链接，不自动代理图片或公开再分发文件。来源分级表示发布身份，不是事实真伪评分。

## 需要纠正或补充的实施细节

### 6. 数据源状态没有足够验收记录

第33行中国载人航天网址应为cmse.gov.cn，方案写为cms.gov.cn。已通过[官方网站](https://www.cmse.gov.cn/)核对。

“JAXA/Roscosmos/ISRO/CNES可用”“均有官方RSS兜底”等表述范围过宽。建议每源列出准确入口、接口/路由版本、测试时间、解析条数、字段样本与从部署服务器的测试结果。本次工具未能成功解析NASA/ESA RSS、SNAPI接口和相关RSSHub路由；这是本次检查的限制，不证明这些接口不可用，也不能替方案确认“已实测”。

NASA旧版APOD接口2026-12-01归档的说法有[官方门户搜索结果](https://api.nasa.gov/index.html)支持，不应当作明显错误；但APOD不属于当前首版核心功能，可后置，避免为非核心接口增加工作。

### 7. 模型价格与一万次请求估算应重算

第181—195行没有具体计价版本、币种、输出单价和缓存比例。以方案的2k输入、500输出计算，一万次调用对应2000万输入和500万输出token，不包含系统提示、历史、检索内容或重试。

审核时[DeepSeek官方定价页检索结果](https://api-docs.deepseek.com/quick_start/pricing/)显示deepseek-flash分峰谷价：非缓存输入每百万token为0.15/0.30美元，输出为0.60/1.20美元。全部请求都调用模型且输入不命中缓存时，以上规模约6/12美元；即使输入全部命中提供商缓存，输出费用仍在。因此原文“几元人民币量级”不能按默认条件成立。

网站答案缓存可以完全跳过部分调用，但必须注明命中率。缓存键应包括文档版本、问题、对话条件、输出类型和提示模板版本；含否定、时间、对象差异的问题不能仅凭相似度共用答案。

智谱[GLM-4-Flash-250414官方文档](https://docs.bigmodel.cn/cn/guide/models/free/glm-4-flash-250414)可访问，但本次未完整核对所有模型免费额度及账户限制。没有据此把“Flash系长期免费”一概认定正确。接入前使用具体模型ID与账户限额实测。价格变动无需阻止开发，应把预算写成公式与日限额。

OpenAI兼容格式可以复用基础请求代码，不保证切换零改动。各供应商的JSON约束、流事件、思考开关、temperature支持和限流行为需要适配测试。先选择一主一备，避免同时接五个平台。

### 8. SQLite中文检索及数据库字段需要设计

第160行的SQLite全文检索未说明中文分词。FTS5默认tokenizer不能直接当作完整中文词语检索方案；可以采用术语别名/分词后索引，或trigram并处理短词。trigram全文查询对少于三个字符的子串有限制，例如“轨道”不能简单依赖该策略。

依据：[SQLite FTS5官方说明](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)。

允许published_at缺失并保留日期来源与解析状态，fetched_at单独存储；不能用采集时间冒充发布时间。补published_at/source_id索引、来源条目ID、更新时间、版本、采集失败原因。title_hash只是精确哈希，不实现相似度。SQLite迁移由写入并发、部署模式及实际性能决定，不单按条数。

### 9. 部署及Agent排得过晚，采集范围过大

第206—212行先扩展全部国内外来源，再做特色栏目、部署，最后做Agent。可能花完时间只得到普通聚合网站。工作量缺少输入权限、联通性和测试等前提。

建议按以下里程碑重排，日期是目标，取决于持续投入和接口实测：

| 时间 | 目标 |
|---|---|
| 10/5—10/7 | 明确三栏目与Agent输出；从阿里云验证2—3个源和一个模型；上线最小空壳与健康检查 |
| 10/8—10/11 | 少量新闻真实入库展示；选一篇材料打通双版本输出、依据和资料不足处理；两项共同成为首版 |
| 10/12—10/15 | 资料库管理员上传与下载；补新闻筛选、权限、文件元数据与缓存 |
| 10/16—10/18 | 固定评测、引用/单位/缺失处理、采集故障与恢复验证；冻结核心功能 |
| 10/19—10/25 | 小范围试用、备份恢复、修复稳定性问题 |
| 10/26—11/2 | 留给后续材料准备及网站维护，避免大改 |

APOD、公众号采集、全来源覆盖、多源事件聚合后置。2核2G首版用Nginx、单worker FastAPI、SQLite、外部模型API；采集定时任务确保只运行一个实例，不能随每个Web worker重复启动。RSSHub按已验证路由需要再加，不预先部署全套浏览器抓取。配置容器内存限制、SQLite持久卷、一致性备份、日志轮转、请求超时及模型任务并发上限。若有SSE，反向代理要处理缓冲与超时。域名、HTTPS、服务器实际出网、磁盘与带宽在第一阶段验证。

## 首版验收应写入方案

1. 2—3个来源可重复采集，不重复入库；单源失败不影响已有列表，发布时间缺失明确展示。
2. 至少一篇真实材料能输出专业摘要与科普版本，关键事实对应可打开的证据；未提供参数有明确不足提示。
3. 固定案例覆盖数值、单位、条件、引用、缺失与恶意指令；上线前抽查严重错误不得隐瞒，按失败范围限制功能。
4. 管理员可发布文件；访客不能获得管理权限，能真实下载；重建容器后资料与记录仍在。
5. 测量并记录响应时延、并发失败、内存峰值与API用量，不从服务器规格推断支持人数。

## 最终建议

保留技术主线，先修范围、证据链、去重、费用与工期。重点投入“事实忠实的科普适配”，新闻聚合与资料下载作为入口和支撑，避免以采集源数量代替作品价值。
